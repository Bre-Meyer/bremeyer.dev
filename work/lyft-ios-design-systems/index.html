Quick-Look

I led the development of QuickLook, a lightweight preview experience for saved inspiration.

QuickLook is a production feature I led end-to-end at The Knot Worldwide, from planning and technical coordination through development and launch. The feature shipped to millions of users and resulted in a 1.7% lift in couple bookings, making it one of the most impactful projects I’ve worked on.

As the engineering lead, a significant part of my role was project planning and task breakdown. In earlier projects, I typically planned work from a purely engineering perspective, mapping out components, architecture, and implementation details up front. While that approach ensured technical clarity, it often required a large upfront investment and didn’t always translate cleanly to product or QA workflows.

For QuickLook, I intentionally tried a different approach: splitting work into user stories instead of technical tasks. Each ticket was written from the user’s perspective with concrete, testable acceptance criteria (for example, “When a user taps the Quick Look button, the app navigates to a new page”). This made scope clearer for cross-functional partners and ensured that QA could validate behavior without needing deep implementation context. I also explicitly accounted for edge cases like loading, error, and empty states to avoid late surprises.

Once the user stories were defined, I reviewed them through a technical lens to identify work that required larger infrastructural changes, such as introducing a coordinator layer to handle navigation. Those efforts were split into developer-only blocking tickets, allowing the user-facing stories to remain focused while still unblocking the necessary groundwork.

What I learned from this project is that leading with user-centric planning significantly improved clarity and velocity, especially for QA and product alignment. That said, the lighter upfront technical planning did result in some mid-development discussions around implementation details. In hindsight, I’ve found the best balance is a hybrid approach: starting from user stories, but pairing them with just enough technical scaffolding to reduce ambiguity.

I’m proud to showcase QuickLook because it’s a real, shipped feature in a widely used app with measurable business impact. Just as importantly, it represents a hands-on learning experience in technical leadership, project planning, and adapting my process to better support both developers and cross-functional partners.

Style Quiz

This was my long-running "pet project" at The Knot and the place where I experimented the most with SwiftUI layouts and animations.

Building My First Production SwiftUI Feature at The Knot

The Style Quiz was the first major feature where I really got to push SwiftUI into a UIKit-heavy codebase at The Knot. Honestly, it became the project where I learned, experimented, broke things, fixed things, and gradually shaped the patterns I’d use across the rest of my time on the team.

When I picked up the feature, it had already gone through a couple of reskins and reworks over the years. My version started as a fairly simple swipe-through questionnaire, but the more I worked on it, the more it evolved into a proving ground for SwiftUI patterns, architectural experiments, and reusable components that eventually made their way into other parts of the app.

⸻

Introducing SwiftUI into a UIKit World

The Knot’s iOS app was almost entirely UIKit at the time, and SwiftUI was still new to the company. Integrating it wasn’t as simple as dropping in a few views. You had to think about how it talked to UIKit navigation, what controlled what, and how state flowed between the two worlds.

The first challenge was navigation. Because the Style Quiz lived inside an existing UIKit flow, I had to wrap SwiftUI screens inside hosting controllers that played nicely with UIKit while still letting me build the quiz UI declaratively. At the time, our patterns for this were still evolving, so I had to invent a few along the way. Some were messy in retrospect, but they all taught me valuable lessons about UIKit/SwiftUI boundaries.

Handling dynamic actions coming back from SwiftUI was another hurdle. When a user made a choice on a SwiftUI screen, UIKit needed to know which next screen to show, how to structure the flow, and how to pass data along cleanly. Early on, that part of the architecture got tangled pretty fast, but each reskin gave me a chance to clean it up, abstract it, or replace the janky parts with something more maintainable.

⸻

The Architecture: A Study in Iteration

If you looked at the Style Quiz architecture over time, you’d be able to see my growth as an engineer in real time.

My early implementation leaned heavily on UIKit coordinators pushing hosting controllers with closures and enums describing “next steps.” It wasn’t pretty, but it worked. Later, as I rewrote and reskinned the feature multiple times, I gradually refactored it toward a more MVVM-inspired pattern: view models driving SwiftUI views, coordinators handling flow, and cleaner boundaries between presentation and logic.

Each iteration was an opportunity to revisit past decisions, fix the brittle parts, and try new patterns. I didn’t get everything right. I had experiments that aged poorly within a few months, but that willingness to iterate ended up shaping the foundation for the architecture patterns I later helped introduce at a team-wide level.

⸻

Reusable Components That Lived Beyond the Quiz

One of the most satisfying parts of this project was building components that ended up being used all over the app.

Masonry Grid Layout

One reskin introduced a layout that needed a Pinterest-style two-column masonry grid. I ended up building a custom SwiftUI layout that handled variable heights, dynamic content, and smooth scrolling. That component later became a key part of the revamped onboarding experience and other style-based flows, and the team has continued using masonry patterns inspired by it.

Progress Bar Style

The Style Quiz needed a custom progress bar that matched the visual brand. I turned it into a reusable progress style, and from there it started popping up everywhere: onboarding, RSVP flows, multi-step forms, and basically anything with a numbered sequence.

Hosting Controller Patterns

Before we had official conventions, I built a custom “union-compatible” hosting controller that handled some of the quirks between UIKit navigation and SwiftUI screens. It wasn’t glamorous, but it became a go-to wrapper for a while until a new team formalized the approach.

Even components I didn’t build for the quiz originally, like my CachedWebImage view, wound up being used in it because it became the team’s standard for displaying web images in SwiftUI.

⸻

Team Impact and SwiftUI Adoption

Style Quiz was also the first feature where I started showing the team that SwiftUI could work in production. I was still early in my SwiftUI journey, but I shared everything I learned: what worked, what didn’t, how state flowed, where UIKit still needed to step in, and how we could make SwiftUI screens play nicely within existing flows.

I hosted code-alongs, built examples, and answered questions practically every day. People were excited, and my manager encouraged me to keep pushing those learnings team-wide. Over time, Style Quiz became one of the internal “reference points” for how real features could be built using SwiftUI.

⸻

What This Project Taught Me

Looking back, Style Quiz was where I learned how to ship SwiftUI at scale, not just build cute prototypes.

It taught me how to:

  • evaluate architectures and refactor them over time
  • gracefully bridge SwiftUI and UIKit
  • create reusable components that scale across multiple features
  • debug “invisible” state bugs and navigation oddities
  • embrace iteration instead of trying to design everything perfectly upfront
  • teach others what I was learning and help them navigate the same patterns

Professionally, it was the project that helped me grow past “the person excited about SwiftUI” into someone who could actually build with it in production, share the knowledge, and shape how our team approached new features.

Dynamic Decoding Utility

This project serves as an example of my engineering style. It's a lightweight decoding utility that decodes strongly typed models from deeply nested JSON using leading-dot syntax.

Because most of my professional work lives in proprietary production code, this project serves as a public, inspectable example of my Swift engineering style. It was built during “10% time” at The Knot and is intentionally small and heavily documented.

The motivation came from a recurring frustration: large JSON payloads where the data I actually cared about was buried several levels deep. Decoding even a small piece of that data often required building full model trees or multiple CodingKey enums just to reach one nested value. The resulting code felt noisy, and overly coupled to the shape of the payload.

My goal was to make this process simpler and more ergonomic. Ideally, I wanted to be able to call a decode function directly on JSONDecoder, pass in a target type and a path, and have the decoder traverse the JSON for me without requiring me to define or care about the structure of every intermediate level. I specifically wanted the API to feel natural in Swift, using leading-dot syntax to describe the path.

To support this, I built a custom JSONDecoder extension backed by a lightweight intermediary type responsible for tree traversal. I initially explored a struct-based approach, but while working through keyed vs. unkeyed containers and string vs. integer keys, I ran into complexity around mismatched containers and invalid key types. That friction led to an important realization: the intermediary itself should be an enum, with cases for the container types and associated values representing the keys. This design ensures that keys and containers always stay in sync, eliminating an entire class of errors.

For traversal, I took inspiration from SwiftUI’s view and modifier system, where each modifier returns a new view instance. I applied the same idea here: each step along the decoding path returns a new instance of the decoding container, carrying forward the accumulated traversal state. While the concept is abstract, the result is both lightweight and composable, with the entire implementation coming in under 200 lines of code (including documentation).

To make the API feel natural to use, I leveraged @dynamicMemberLookup, allowing arbitrary paths to be expressed using dot syntax. Under the hood, this is powered by a DynamicDecodingKey that conforms to CodingKey but can be initialized with any string, making it possible to decode values for arbitrary keys without predefining enums. This piece is what gives the utility its flexibility and reusability.

The end result is a decoding extension that can extract strongly typed models from deeply nested JSON while remaining completely agnostic to the shape and structure of the data along the way. I have plans to extend this approach further to support key-path decoding directly on decoding containers, but that work is still in progress.

If you download the included Swift playground, you can explore interactive, runnable examples embedded directly in formatted documentation and experiment with the API yourself.
